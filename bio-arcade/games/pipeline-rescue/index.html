Reproducible computing · workflows as DAGs

The run died at 2 a.m. — rescue it without rerunning the world.

Real analyses are not one script but a workflow: tasks wired by their inputs into a directed acyclic graph (DAG). A task can run the moment its inputs exist — which is also how engines like Nextflow and Snakemake know, after a crash or a change, exactly which results are still valid: anything whose inputs did not change stays cached; anything downstream of a change is stale and must rerun. That is cache-and-resume, and it is why a fixed typo costs minutes, not the whole week of compute. The other lesson of the night shift: pipelines usually die of metadata — wrong sample IDs, wrong reference version — not of broken code.

After playing you can…
  • Wire a task to its real inputs and explain why the graph must have no cycles.
  • After a crash, name the ROOT CAUSE task (where the problem lives) versus where the error appeared.
  • After a fix or an input change, name exactly which tasks are stale (must rerun) and which cached results are still valid.
  1. 1Wire it: for each task, tap the inputs it actually needs — the arrows you choose become the DAG.
  2. 2Rescue it: the run fails. Tap the task where the ROOT CAUSE lives, pick the right fix, then queue EXACTLY the stale tasks for the resume — rerunning a cached task wastes compute, missing a stale one ships wrong results.
  3. 3Every valid cached task you protect banks CPU hours. First 2 wrong taps are free practice; after that, 3 slips kill the run for good.
